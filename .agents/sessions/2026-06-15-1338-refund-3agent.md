# Session: Refund flow — 3-agent parallel build

_2026-06-15 ~13:38_

## Goal
Build the refund feature (next-step #2), using the parked scaffold. User decisions:
- **Flow**: customer requests → Owner/Admin approve.
- **Money**: credit to customer **Wallet**, with a **Manual** option too (owner refunds off-system, record only).

## Approach
Same as the LINE feature: orchestrator lays the shared foundation (so the 3 agents never touch the same
file), then fans out 3 parallel agents (App/Owner/Admin), then integrates + verifies. Custom agent types
aren't registered as `subagent_type`, so spawned as general-purpose with role/zone embedded in the prompt.

### Foundation (orchestrator)
- `refunds` table + `Refund` model (already scaffolded earlier) — now wired.
- `Booking`/`Payment` got a `refunds()` HasMany.
- **`app/Services/RefundService.php` (NEW, money-critical, shared)** — the wallet-credit + state transition
  logic in ONE place so Owner & Admin can't diverge: `approve(refund, method, note, processedBy)` (DB
  transaction; guards `status===requested`; `wallet` → credit customer wallet + WalletTransaction + booking
  `cancelled`; `manual` → record only) and `reject(...)`.
- `routes/api.php` — 7 routes pre-registered (customer POST /bookings/{id}/refund + GET /refunds; owner +
  admin index/approve/reject).
- `lib/types.ts` — `Refund`, `RefundStatus`, `OwnerRefund`, `AdminRefund`.

## Design notes
- Refund destination = wallet credit (no gateway, fits the existing wallet system) OR manual (off-system).
- Approve sets booking `status='cancelled'`. Full-amount only for now (schema's `amount` supports partial later).
- Money logic centralized in `RefundService` (DB transaction + idempotency guard) — Owner & Admin both call it.
